# 修复记录（dxf-editor · 已修复的显示 Bug 及修复方法）

> 每个条目按「现象 → 根因 → 修复 → 验证」四段式记录，含涉及文件与时间。
> 程序化验证方式说明：本项目模型无法看图，全部用 **Playwright 无头 + `getImageData` 像素统计 + 几何解析断言** 做验证。

## 1. 「小高电气」28 张图重叠 vs CAD 只显示 3 张（核心）— 2026-08-16/17

- **现象**：`小高电气平面图_t3.dxf` 在 AutoCAD/GstarCAD 只显示 **3 张图（1 行×3 列：动力/报警/防雷接地）**，网页却显示 **4 列×7 行 ≈ 28 张重叠**。
- **根因**：文件把外部参照绑定为块 `小高平面图`，顶层 4 个 INSERT（handle `38A/7A6/11943/2329C`）**每个都带 `AcDbSpatialFilter`（XCLIP）**。扩展字典链 `INSERT(360=xdict)→DICTIONARY(ACAD_FILTER)→DICTIONARY(SPATIAL)→AcDbSpatialFilter` 保存了裁剪矩形；旧 `flatten()` 完全忽略裁剪，把每个 INSERT 的整块 4×7 内容全展开 → 28 张重叠。
- **修复**：
  - `dxf-parser.js` 新增 `extractSpatialFilters()`：解析 SPATIAL_FILTER 的 group-40 前 12 值 → 3×4 仿射矩阵 `FILTER_M`（filter-ECS→块坐标系）；沿 owner(330) 链回溯到 INSERT 并挂 `spatialFilter`。
  - `flatten()` 遇到带裁剪的 INSERT：裁剪边界经 `FILTER_M` 映射到块系，再经 `INSERT_M`（`nm`）映射到世界系，与父裁剪求交后传给子实体，叶节点附加 `_clip`。
  - `dxf-render.js` 按 `e._clip` 分组，`ctx.clip()` **硬裁**，长构造线不跨出图框。
- **验证**：裁剪后 4 个 INSERT 世界矩形落在 3 个水平条带（`38A` 与 `7A6` 重合），X 总跨 `253301→706639` = CAD `$EXTMIN/$EXTMAX` 完全吻合；active 实体 **537974 → 38068**；46 文件回归 0 错误 0 空白；Playwright 截图确认 3 张干净图纸。

## 2. 白线随缩放忽明忽暗（1px 发丝线反走样闪烁）— 2026-08-19

- **现象**：`结施变-01-…KZ4_t3.dxf`（1127 条白线）随 zoom 白线闪烁，放大到 scale≈20+ 时白线几乎全消失；绿线仍可见。
- **根因**：所有描边 `lineWidth=1`。1px 线居中在整数设备像素时覆盖 [x-0.5, x+0.5] 跨两像素各 50% → 渲染成约 50% 灰（实测中心像素 (112,112,112) 而非 (255,255,255)）；随 zoom/pan 相对像素网格移动而闪烁，极倍缩放时全落灰色态、白色计数归零。
- **修复**：`dxf-render.js` 的 `_pathEntity`/`_loopPath` 顶部把传入 `SX/SY` 重定义为 **`SX = x => Math.round(_sx(x)) + 0.5`**（像素中心吸附）。1px 描边始终精确覆盖一整像素 → 任意缩放纯亮白。仅影响描边坐标（≤0.5px），不影响填充/文字/XCLIP 裁剪框。
- **验证**：修复前 scale≈20 时 white=0；修复后同条件下 white=728 纯白（255），极倍缩放（scale≈644）稳定可见。无回归。

## 3. Defpoints 层"像素点"网页显示、CAD 不显示 — 2026-08-19

- **现象**：网页端出现大量像素点（POINT），商业 CAD 不显示。
- **根因**：Defpoints 层（尺寸/引线定义点层）3128 个 POINT，AutoCAD 默认隐藏该层定义点。
- **修复**：`dxf-render.js` POINT 分支 `if (/^defpoints$/i.test(e.layer)) return;`——只跳过 Defpoints，保留其余 577 个设备层 POINT。
- **验证**：POINT 跳过计数 3128/3705；46 文件回归 PASS。

## 4. 镜像门块弧线方向颠倒（门框方框线条错乱）— 2026-08-19

- **现象**：门块 `DorLib2D$00000002`（8 LINE+2 ARC）被镜像 INSERT（`det<0`，sx/sy 异号）引用后，弧画反方向，门框线条错乱。
- **根因**：`xformEntity` 旧 ARC 镜像公式 `180−angle+rot` 只对 y 轴镜像（sx<0）正确，x 轴镜像（sy<0）画反。
- **修复**：`dxf-parser.js` 用 insert 矩阵精确变换弧端点：`atan2(m.b·cosθ+m.d·sinθ, m.a·cosθ+m.c·sinθ)`，镜像时交换起止角。
- **验证**：12 个镜像门实例 × 2 弧端点 = 32/32 命中真实变换几何（旧公式 0/32）。

## 5. 文字被填充/线条遮挡 → 文字置顶 — 2026-08-19

- **现象**：绿色填充/线条遮挡文字（如"消防强电金属防火"）。
- **根因**：`_drawEntityList` 在每个 XCLIP 裁剪组内"先几何后文字"，后绘制的裁剪组几何覆盖先绘制组的文字。
- **修复**：`_drawEntityList` 支持 `opts.skipText` 只画几何并返回文字；`render()`/`_drawEntities()` 先遍历所有裁剪组画几何，再统一遍历画文字（仍尊重各自裁剪区）。
- **验证**：合成 HATCH+TEXT 分属不同裁剪组，文字区域 white=400、green=0（PASS）；46 文件回归 PASS。

## 6. 框选文字把框外附近文字也选进来 → 范围精确化 — 2026-08-19

- **现象**：框选文字时把框外不远处文字也识别。
- **根因**：`finalizeTextPick` 把框向四周扩展 25%+8px 并把"周边"文字纳入。
- **修复**：删除扩展容差与 `near` 标记，只识别包围盒与真实框选矩形相交的文字；`showTextPick` UI 去掉"含周边"提示。
- **验证**：单元测试：仅框内/相交文字入选、框外不远不入选（PASS）。

## 7. 闭合宽多段线未填充（设备块显示斜线而非"亮绿色实心"）— 2026-08-19

- **现象**：`小高电气平面图_t3.dxf` 设备块（照明配电箱）网页端只显示 45° 电气斜线，商业 CAD 显示**亮绿色实心 + 斜线**。
- **根因**：设备块外框是**闭合且带宽度**的 LWPOLYLINE（`constWidth=0.04`，`f70=0` 但首尾顶点重合=几何闭合），AutoCAD `$FILLMODE=1` 会把内部填充成图层色（绿）；网页端原先只画中心线/外框、未填充。*注：初版"凡闭合宽多段线就填充"会把 `PUB_TITLE` 巨框（71800×28700）也填成青色覆盖全图——这是第二个坑。*
- **修复**（`dxf-render.js`）：
  - `_isWideClosedPoly()`：闭合判定（`f70&1` / 首尾重合 / 首点在后续顶点重现形成回路）+ 宽度>0（`constWidth` 或顶点 start/endWidth）。
  - `_isFillablePoly()`：再加「**世界包围盒短边 / 整图短边 < 1%**」门栏——设备块（短边≈60，占比≈0.01%）填充；`PUB_TITLE` 图框（短边 28700，占比≈4.6%）保持空心。为什么用世界短边：`constWidth` 不会被块变换缩放（仍是局部值），纯世界坐标比较最稳。
  - `_getDocBounds()`：惰性计算并缓存所有空间实体的并集包围盒。
  - `_drawEntityList` 第 1 遍新增 `_fillPoly`；第 2 遍线批次跳过已填充实体。
- **验证**：设备块区域像素计数 **90.1% 绿 / 0% 青**（修复前 0%）；禁用填充对照仅 3.9% 绿（=仅外框+斜线）；效果图 `docs/equip_fill_fix.png`；46 文件回归 PASS。

## 12. 新增：二进制 DXF 格式支持（功能新增，非 Bug）— 2026-08-20

- **现象/需求**：用户希望能直接打开 AutoCAD「另存为 → 文件类型 → Binary DXF」保存的文件，且**显示必须与同一张图的 ASCII 版本完全一致**。
- **根因（此前为何打不开）**：Binary DXF 以 22 字节哨兵 `AutoCAD Binary DXF\r\n\x1A\0` 开头，后续组码/值均为二进制编码（双精度 8 字节大端、短整 2 字节、长整 4 字节、字符串 2 字节长度前缀 + 字符等），旧 `decode()` 只按文本解码，必然乱码/解析失败。
- **修复**（`dxf-binary.js` 新增 + `dxf-parser.js`/`index.html` 集成）：
  - 新增 `dxf-binary.js`：导出 `isBinaryDxf()`（哨兵检测）与 `binaryToText()`（按组码→数据类型映射逐对解出值，输出与对应 ASCII DXF 完全等价的字节流；**字符串字段保留原始字节**交由下游 `decode()` 做 UTF-8/GBK 嗅探，数值按真实 double/int 文本化）。
  - `dxf-parser.js` 的 `decode()` 字节分支开头：`if (DxfBinary.isBinaryDxf(u8)) u8 = DxfBinary.binaryToText(u8);` 之后走标准解码——**复用 100% ASCII 管线**。模块顶部用 `require('./dxf-binary')`（Node）或 `global.DxfBinary`（浏览器）引入，带 try/catch 容错。
  - `index.html`：在 `dxf-parser.js` 之前加载 `dxf-binary.js`（`?v=20260820`）。
- **为何显示与 ASCII 一致**：本模块仅做「二进制 → 等价 ASCII 字节流」的格式翻译，下游 `parse/flatten/render` 与 ASCII 完全相同，故渲染像素必然一致（也见 README 第四节第 6 条）。
- **验证**（程序化，Node 自洽测试，运行后已清理临时脚本）：
  1. **解码方向独立验证**：手工构造二进制 buffer（不依赖编码器）→ `binaryToText` 还原出的 ASCII 与手工期望**逐字节一致**（哨兵识别 + 各类型解码正确）。
  2. **端到端一致性**：把一份含中文 TEXT 的 ASCII DXF 编码成二进制再解析，实体类型/坐标/图层/颜色/插入参数/多段线顶点与直接解析 ASCII **逐项相同**；中文「墙体厚度200」解码一致。
  3. **数值精度无损**：`123.456789012345`、极小负数 `-1.23e-7` 均精确往返（double 最短表示）。

## 13. 文字显示过小（白点/小横线）— 2026-08-20

- **现象**：打开建筑平面图后，文字变成几乎不可辨的白色小点或小横线（用户截图反馈），与 AutoCAD 打开同一张图时清晰可读的标注明显不一致。
- **根因**：
  - DXF 中 TEXT/MTEXT 的 group 40（字高）为 `0` 时，语义是「使用文字样式 (STYLE) 的固定高度」；样式高度也为 `0` 时回退到 `$TEXTSIZE`。原渲染器直接 `Math.abs(e.r40 || 2.5)`，把 `0` 当成未设置并硬编码回退到 `2.5` 图形单位，对毫米单位建筑图几乎看不见。
  - 块参照内的文字字高没有随块插入平均缩放 `sc` 变换，导致块内文字与周围几何比例失调。
- **修复**：
  - `dxf-parser.js` `xformEntity(e, m, doc)`：块展开时若文字 `r40 <= 0`，按 `STYLE.height → $TEXTSIZE → 2.5` 解析，再把结果乘 `sc` 得到世界字高。
  - `dxf-render.js` 新增 `_resolveTextHeight(e)`：渲染前统一解析（顶层文字未经过块变换，也走同一规则）。
  - 文字包围盒估算、`_drawTextSys`、`_drawTextShx` 全部改用 `_resolveTextHeight()`。
- **验证**：Node 自洽测试：构造 `TEXT(r40=0)` + `Standard 样式 height=50` + `INSERT(sx=sy=5)`，展开后块内文字字高 = `50×5 = 250` 世界单位；46 文件回归 `ok=46 / err=0`。

## 14. 打开文件「展开失败」（回归）— 2026-08-20

- **现象**：装上第 13 条（文字修复）后，一打开含文字（TEXT/MTEXT/ATTRIB）的 DXF 就弹出「展开失败」，整图无法显示。
- **根因**：`dxf-render.js` 的 `bbox()` 是独立函数（非方法），在 `R.load()` → `_prepare()` 里以 `bbox(e)` 自由函数方式调用，内部 `this` 指向全局对象而非渲染器实例。第 13 条把文字包围盒分支改成 `this._resolveTextHeight(e)`，于是 `this._resolveTextHeight` 为 `undefined` → 抛 `TypeError` → 被 `app.js` 的 `R.load()` 捕获并提示「展开失败」。修复前该分支用 `e.r40 || 2.5`，不依赖 `this`，故此前正常。
- **修复**：给 `bbox(e, self)` 增加 `self` 参数，文字分支改为 `self && self._resolveTextHeight ? self._resolveTextHeight(e) : (e.r40 || 2.5)`；所有调用点（`_prepare` / `_getDocBounds` / `_isFillablePoly` / `_computeBounds` / `bboxOf`）传入 `this`。缺少渲染器时仍安全回退 `e.r40 || 2.5`。
- **验证**：Node 端到端镜像 `app.js` 的 `loadBuffer`（`decode→parse→new DxfRenderer(mockCanvas)→R.load(doc)`），对含 6 / 4 个文字实体的 DXF 实测 `R.load` 不再抛错；`bbox` 对单个文字实体也正常。

## 15. 线条随 zoom 缩放显隐（白线灰↔白闪烁）— 2026-08-20

- **现象**：细线（尤其白线）随滚轮缩放/平移在「灰（看不见）↔ 白（清晰）」间闪烁，图中细线"时隐时现"。
- **根因**：发丝线吸附只做了 CSS 像素层 `round(x)+0.5`，而画布用 `setTransform(dpr,…)` 缩放。仅 `dpr=1` 时 CSS 半像素=设备像素中心；Windows 125%/150% 缩放（`dpr=1.25/1.5`）下吸附对齐的是 CSS 半像素、**并非真实设备像素**，1px 线仍跨两设备像素各约 50% → 抗锯齿成灰并随 zoom 闪烁。原始 `round+0.5` 修复在 dpr≠1 时不彻底。
- **修复**：`_pathEntity()` 与 `_loopPath()`（HATCH 边界 1px 线）的吸附改为按 `dpr` 对齐设备像素中心：`Math.round(x*dpr)/dpr + 0.5/dpr`（使 `snappedCss*dpr` 落在半整数）。模型路径与图纸/视口路径都经 `_pathEntity`，一并生效。
- **验证**：Node mock 画布构造 `DxfRenderer(dpr∈{1,1.25,1.5,1.75,2,3})` 对 LINE 调用 `_pathEntity`，校验顶点 `2×(snappedCss×dpr)` 均为整数：6/6 PASS。

## 16. 线条随 zoom 缩放显隐（最终方案：2x 超采样）— 2026-08-20

- **现象**：第 15 条按 dpr 吸附设备像素的方案在 125%/150% 缩放下仍有改善，但用户实测反馈**斜向细线（尺寸线、引线等）随 zoom 仍会出现灰↔白闪烁**，截图中箭头所指白线在某些缩放级别几乎消失。
- **根因**：发丝线吸附只能让水平/垂直线稳定落在设备像素中心；对于**斜线**，无论如何调整顶点位置，线段必然跨越多行/多列设备像素，子像素覆盖率仍会在 zoom/pan 时跳变。单像素线宽处于 Canvas2D 抗锯齿敏感区间，dpr 吸附无法根除斜线闪烁。
- **修复**：把整帧绘制改为 **2x 超采样渲染**：
  - `render()` 创建/复用一块 2 倍设备分辨率的离屏 canvas（`W×H×dpr×2`）。
  - 所有几何、填充、文字、高亮、overlays 先绘制到离屏 canvas（变换矩阵也乘以 2）。
  - 最后用 `drawImage()` 线性缩放回显示 canvas；每个显示像素由 4 个子像素平均，覆盖率变化连续化，斜线/细线不再在「灰↔白」间跳变。
  - 文字与线宽视觉大小保持不变（绘制时放大 2 倍再缩小）。
- **实现**：`dxf-render.js` 新增 `_offCanvas/_offCtx` 与 `_blitOffscreen(W,H)`；`render()` 内绘制目标从 `this.ctx` 切到离屏 ctx，所有子函数仍通过 `ctx` 参数接收，无需改动。`index.html` 缓存戳升 `v=20260820d`。
- **验证**：语法检查通过；Node mock 端到端确认 `render()` 不再报错、`_blitOffscreen` 调用链路正确。最终效果需浏览器实测确认。
